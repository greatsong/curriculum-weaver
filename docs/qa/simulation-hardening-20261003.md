# 시뮬레이션 강건성 수정 검증 — 2026-10-03

## 수정한 실패 경로

- 신규 생성에서 일부 보드만 저장되거나 빈 보드가 반환되어도 완료로 표시되던 문제: 전체 19개 절차의 스키마와 저장 결과를 검사한다.
- 읽기 권한(viewer)으로 신규·이어서 생성할 수 있던 문제: 기존 프로젝트 생성과 동일한 owner/editor 경계를 적용한다.
- 여러 탭·서버의 중복 생성과 일일 한도 경쟁: Supabase 트랜잭션에서 실행 예약과 UTC 기준 일일 10회 한도를 함께 처리한다.
- 연결 재시도에 따른 중복 생성: 요청 ID를 유지하고 기존 프로젝트 ID를 반환한다. 입력이 바뀌면 새 요청을 만든다.
- 서버 중단 후 영구적인 생성 중 상태: 30초마다 실행권을 갱신하며 5분 만료/최대 30분을 적용한다. 부팅 및 1분 주기 복구로 실패 상태로 전환한다. 기존 작업 중 30분 이상 된 미등록 생성 중 프로젝트도 복구한다.
- 실행권을 잃은 서버: AI 호출에 중단 신호를 전달하며 저장 전 실행권을 재확인한다.
- 신규 생성 메타데이터 누락: 학년·교과·생성자를 저장한다.
- 잘못된 입력 자료형과 예상 밖 AI 응답: 400 응답 또는 실패 처리하며 완성된 결과로 세지 않는다.
- SSE 시작/완료 이벤트 유실: 신규·이어서 화면에서 기존 프로젝트를 조회해 복구한다. 시작 ID도 유실되면 같은 요청 ID로 재시도한다. 권한 상실·조회 시간 초과·화면 이탈도 처리한다.
- 작업 성공과 프로젝트 완료 상태는 한 DB 트랜잭션으로 확정한다. 실패한 프로젝트의 부분 결과는 보존한다.

## 자동 테스트

- 서버: `npm test --workspace=server -- --maxWorkers=2`
- 클라이언트: `npm test --workspace=client -- --maxWorkers=2`
- 빌드: `npm run build`
- 미래보기 A-3 → A-4 → 이어서 시뮬레이션 → HTML/Markdown 보고서, 원본·성취기준 보존, 복제 실패, 건너뛰기, 읽기 전용, 빈 결과, 부분 저장, 연결 중단을 포함한다.
- 전체 테스트와 빌드를 과도하게 병렬 실행했을 때 기존 테스트 2개에서 시간 초과가 발생했다. 워커를 2개로 제한하고 전체를 다시 실행하여 통과했다. 테스트 제외나 시간 제한 상향은 하지 않았다.
- 테스트가 해당 체크아웃의 shared 패키지를 사용하도록 alias를 명시했다. 클라이언트 테스트 JSX는 실제 앱과 같은 automatic runtime을 사용한다.

## 실제 Supabase 검증

마이그레이션 `00028_simulation_runs.sql` 적용 후 다음 명령으로 12개 검증을 통과했다.

```sh
node --env-file=server/.env scripts/qa/verify-simulation-runs.mjs --live-verify
```

동시 12회 요청의 10회 제한, 동일 요청 8개의 단일 예약, 요청 ID 재사용 시 입력 불일치 거절, 성공 종료, 프로젝트 상태·최종 단계 동시 확정, 새 연결에서 완료 결과 복구, 다른 사용자 동시 요청 차단, 만료 프로젝트 실패 복구, 만료 실행권 재사용 차단, 부분 결과 보존, 실패 후 재시도, 익명 키의 RPC 접근 차단을 확인했다. 시험용 UUID의 작업·프로젝트만 생성하고 종료 시 정리했다.

## 배포 순서 및 검증 한계

DB 마이그레이션을 먼저 적용한 뒤 서버·클라이언트를 배포한다. DB가 준비되지 않거나 장애가 있으면 메모리 우회 없이 새 생성을 차단한다. PR과 Railway 배포 전에 전체 회귀 테스트·빌드를 실행하도록 CI를 추가했다.

애플리케이션 전체 흐름 테스트의 AI와 DB는 모의 구현이다. 실제 DB의 동시성·복구는 별도 검증했으며, 실제 AI 공급자 장애·생성 내용의 교육적 품질·대규모 부하까지 검증한 것은 아니다. 프로세스 중단 작업을 자동으로 이어 생성하지는 않으며, 부분 결과를 보존하고 원본에서 재시도할 수 있게 한다.
