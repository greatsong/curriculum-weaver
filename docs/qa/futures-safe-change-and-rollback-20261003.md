## 이미 적용된 안전장치

`.github/workflows/verify.yml`은 PR에서 서버 전체 테스트, 클라이언트 전체 테스트, 프로덕션 빌드를 실행한다. Railway 배포는 같은 검증 작업이 성공해야 시작된다. 현재 기준에서 서버 426개, 클라이언트 269개 테스트 및 빌드가 통과했다.

GitHub 병합 보호 규칙은 이번 준비에서 변경하지 않았다. 따라서 PR의 검증 성공을 확인한 뒤 병합해야 한다. Vercel은 main 병합 시 자동 배포되므로, Railway 검증만 믿고 실패한 PR을 먼저 병합하면 안 된다.

## 향후 변경 단위 — 별도 실행 승인 후

각 단계를 별도 PR로 만들어 앞 단계가 운영에서 확인된 뒤 다음 단계로 진행한다. UI 변경·API 삭제·DB 작업을 한 PR에 섞지 않는다.

1. **공유 코드 분리:** 실험실에서 사용하는 색상·선택 상태·과목 묶음·그래프·스타일을 공용 영역으로 옮긴다. 구버전 모듈은 재수출 등 호환 경로를 유지한다. API 주소와 화면 동작은 그대로 둔다.
2. **구버전 화면 정리:** 기존 URL의 처리 방침을 사용자와 결정한 뒤 페이지 전용 코드만 정리한다. `codes`, `model`, 기존 프로젝트 문맥을 보존하는지 검증한다. 실제 사용 중인 `futures2` 서버와 공용 컴포넌트는 남긴다.
3. **구버전 API 정리:** 접근 로그와 이전 브라우저 번들의 호출 여부를 확인한 뒤 별도 PR로 진행한다. 실험실의 `/api/futures2`는 삭제 대상이 아니다. 서버 등록·전용 limiter·테스트 참조를 함께 점검한다.
4. **데이터 정리:** 이번 계획에는 포함하지 않는다. `scenario_cache` 전체 삭제, 프로젝트/성취기준 삭제, sessionStorage 공유 키 삭제는 하지 않는다. 필요하면 백업·복원 검증을 갖춘 별도 승인이 필요하다.

각 PR에는 기준 커밋, 변경 파일, 제거/이전하는 참조, 검증 결과, 되돌릴 커밋 및 앞뒤 단계 의존성을 기록한다.

## 병합·배포 중단 조건

다음 중 하나라도 실패하면 배포하지 않는다. 운영에서 발견되면 다음 정리 단계로 진행하지 않고 해당 변경을 되돌린다.

- 선택한 성취기준으로 연결 그래프와 여덟 관점이 정상 표시되지 않음.
- 새 프로젝트 생성 시 교과·성취기준·제목·설계 의도가 누락됨.
- 기존 프로젝트 A-3 반영에서 원본 내용이 손실되거나 A-4로 이어지지 않음.
- 건너뛰기·읽기 전용·권한 경계가 바뀌거나 시뮬레이션의 부분 실패가 완료로 표시됨.
- 시뮬레이션/보고서에 기존 성취기준 또는 분석 결과가 빠짐.
- 전체 회귀 테스트·빌드 실패, import 누락, 화면의 새 오류, 관련 API의 새 4xx/5xx 오류.

모의 AI/DB 테스트와 실제 서비스 확인은 구분한다. CSS를 분리할 때는 데스크톱·모바일 그래프와 미래 상세 화면을 눈으로 비교하고, 실제 API는 인증된 계정으로 정상·오류 응답을 확인한다. 검증되지 않은 영역을 정상이라고 기록하지 않는다.

## 기본 롤백: 문제를 만든 커밋만 역순으로 되돌리기

원본 작업 폴더에는 다른 작업이 있으므로 깨끗한 격리 체크아웃에서 진행한다. main 전체를 과거로 강제 이동하지 않는다. 아래 `<...>`는 해당 배포의 실제 값으로 바꾼다.

```sh
git fetch origin --tags
git status --short
# 로컬 변경이 없는지 확인 후 새 브랜치 생성
git switch -c codex/revert-futures-<change> origin/main
# 뒤 단계가 앞 단계에 의존하면 뒤 단계부터 함께 되돌린다.
git revert --no-commit <latest_bad_commit> <earlier_dependent_commit>
git diff --cached --stat
git diff --cached --check
npm test --workspace=server -- --maxWorkers=2
npm test --workspace=client -- --maxWorkers=2
npm run build
# 변경 범위를 확인해 커밋하고, PR CI가 통과한 뒤 병합·재배포한다.
```

문제가 한 커밋이면 `git revert --no-commit <bad_commit>`만 사용한다. 충돌이 나면 멈춰 충돌 범위를 검토하며, 일괄 덮어쓰기나 강제 푸시로 해결하지 않는다. 취소는 해당 격리 체크아웃에서 `git revert --abort`를 사용한다(진행 중인 revert가 있을 때).

복구 태그는 원래 파일/동작을 비교하는 기준으로 사용한다. 태그 이후의 다른 정상 수정까지 제거하는 `reset --hard`/force push 배포는 하지 않는다. 호스팅의 이전 배포 즉시 복원 기능을 사용할 경우에도 프론트엔드·서버 버전 조합을 확인하고, 이후 Git에도 같은 복구를 기록해야 한다.

## DB와 배포 후 확인

이 정리 작업에는 DB 변경이 없어야 하므로 코드 롤백 시 DB를 되돌리지 않는다. 특히 PR #144에서 추가한 `simulation_runs`와 기존 프로젝트·성취기준·공유 캐시는 유지한다.

복구 후 `/api/health`, 워크스페이스의 단일 실험실 버튼, 실험실 그래프/미래 상세, A-3 반영, 시뮬레이션 및 보고서를 재확인한다. 프론트엔드 파일이 복구된 버전인지 확인하며, 캐시 때문에 옛 화면이 남으면 새로고침해 확인한다. 각 호스팅 배포의 성공 상태와 실제 응답 확인을 모두 기록한다.

## 준비 단계의 복구 검증

PR #145 변경의 역패치를 임시 Git 인덱스와 임시 객체 저장소에 적용해 직전 정상 트리와 정확히 일치하는 것을 확인했다(통과). 실제 체크아웃·실제 Git 인덱스·운영에는 역패치를 적용하지 않는다. 이 검증은 복구 수단을 확인하는 것이며, 아직 수행하지 않은 미래 코드 삭제의 롤백까지 검증했다는 뜻은 아니다. 각 향후 PR마다 실제 변경을 대상으로 같은 검증과 전체 테스트가 다시 필요하다.
