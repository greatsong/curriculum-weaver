# 미래보기(타임스톤) 기능 명세서

작성일: 2026년 10월 3일 · 버전: 1.1

이 문서는 curriculum-weaver의 **미래보기(타임스톤)**를 처음부터 설계하고 구현할 때 사용할 요구사항과 검수 기준이다. 교사가 선택한 성취기준의 관계를 이해하고, 그 관계를 바탕으로 가능한 융합 수업을 탐색한 뒤 실제 프로젝트 설계로 이어지는 경험을 정의한다.

핵심 흐름은 **성취기준 선택 → 성취기준과 키워드의 소속 관계 표시 → 키워드 간 연결 공개 → 사용자가 ‘미래 보기’ 클릭 → 시간의 고리 연출 → 수업 아이디어 탐색**이다. 연결 공개가 끝났다는 이유로 미래를 자동으로 열거나 생성해서는 안 된다.

‘필수’는 구현 합격 조건이다. 시간·크기·요청 수 등 ‘초기 설계값’은 구현을 위한 제안이며 사용자 요구를 수치화한 값이다. 실제 기기와 운영 부하를 측정해 조정할 수 있지만, 클릭 전 미래 생성 금지와 그래프 관계의 정확성은 유지해야 한다. 마지막 장의 기존 구현 기록은 참고 자료이며, 새 구현의 검증을 대신하지 않는다.

## 1 목적과 이용 상황

처음 방문한 교사가 코드 입력 방법을 몰라도 성취기준을 선택하고, 어떤 내용이 어떤 교과와 이어지는지 이해할 수 있어야 한다. 시각 효과는 교육과정의 관계를 설명하고 미래 탐색에 몰입하도록 돕는다.

주요 이용 상황은 교사 연수에서 약 10명이 동시에 서비스를 사용하는 것이다. 참여자는 각자 프로젝트를 만들거나 팀의 한 기기로 함께 탐색할 수 있다. 같은 프로젝트에 여러 명이 참여하는 협업은 기존 워크스페이스의 권한·멤버십·동기화 기능을 사용한다. 이 기능에서 별도의 실시간 공동 조작 프로토콜을 새로 만들지는 않는다.

완료된 경험에서 교사는 다음을 설명할 수 있어야 한다.

- 선택한 성취기준과 각 성취기준에 속한 키워드가 무엇인지.
- 어떤 키워드들이 이어졌으며, 연결 이유가 무엇인지.
- 그 연결로 어떤 수업을 할 수 있으며 각 성취기준이 어떤 역할을 맡는지.
- 마음에 드는 수업 아이디어를 실제 프로젝트 설계로 가져가는 방법.

## 2 범위와 명칭

| 항목 | 요구사항 |
|---|---|
| 서비스 표시 이름 | 모든 메뉴와 화면 제목에서 `미래보기(타임스톤)` 사용 |
| 진입 경로 | 로그인한 사용자의 워크스페이스에서 진입, 독립 경로 `/futures2` 제공 |
| 선택 수 | 서로 다른 성취기준 2~7개 |
| 스톤 수 | 선택 수와 동일. 같은 과목의 스톤은 같은 색으로 묶어 표시 |
| 미래 탐색 | 첫 버전은 8개 관점의 수업 아이디어 제공 |
| 모델 선택 | ‘빠른’, ‘정밀’ 제공. 공급자 모델 ID는 서버 설정에서 관리 |
| 프로젝트 연계 | 선택 성취기준과 수업 제목·설명을 기존 생성 화면으로 전달 |
| 기존 기능 | 기존 `/futures`, 채팅, 성취기준 탐색, 워크스페이스 흐름 유지 |

타임스톤은 초록빛 시간의 고리와 미래 탐색을 나타내는 시각적 콘셉트다. 특정 작품의 이미지 파일을 가져오는 방식보다 자체 SVG·CSS·Canvas 표현을 사용한다. 전체 교육과정 그래프 개편, 프로젝트 자동 완성, 별도의 팀 동시 편집 기능은 이 명세의 범위 밖이다.

## 3 화면과 사용자 흐름

### 3.1 진입과 안내

로그인하지 않은 사용자는 기존 로그인 흐름을 거치고 요청했던 경로로 돌아온다. 로그인한 사용자는 제목, 모델 선택, 입력 패널, 선택된 성취기준 목록을 본다.

첫 안내 문구는 다음과 같다.

> 성취기준 2~7개를 고르고 연결을 확인한 뒤, ‘미래 보기’를 눌러 수업의 가능성을 엽니다.

빈 화면에는 검색 예시, 교과를 통한 선택 방법, ‘예시 조합으로 보기’를 제공한다. 예시 조합은 실제 성취기준 정본에서 조회해 사용하며, 예시를 누르는 것만으로 미래 생성 API를 호출하지 않는다.

### 3.2 성취기준 입력

입력 수단은 코드·내용 검색, 학교급·교과 목록, 여러 코드 붙여넣기의 세 가지다.

| 입력 방식 | 필수 동작 |
|---|---|
| 코드 검색 | 대괄호·공백·하이픈 유무를 정규화하고 정확 일치를 먼저 표시 |
| 내용 검색 | 교과명과 성취기준 원문을 대상으로 검색. 여러 검색어는 모두 포함하는 결과 우선 |
| 학교급 | 초등·중학·고등·전체. 학교급을 바꾸면 적용할 수 없는 교과 필터 해제 |
| 교과 목록 | 검색어가 없어도 교과를 선택하면 해당 성취기준 목록 표시 |
| 여러 코드 입력 | 쉼표·줄바꿈·세미콜론·탭으로 구분된 코드 및 여러 대괄호 코드 처리 |
| 검색창 붙여넣기 | 여러 코드가 감지되면 일괄 입력 처리. 코드들이 모두 틀려도 오류 안내 |
| Enter | 한글 입력 조합 중에는 실행하지 않음. 조합 종료 후 결과 추가 또는 코드 일괄 처리 |

검색 결과에는 코드·교과명·원문을 표시한다. 선택 목록에는 동일 정보, 색상, 제거 버튼, 현재 선택 수를 표시한다. 동일 교과에서 서로 다른 성취기준을 선택하는 것도 허용한다.

각 성취기준은 고유 `key`로 식별한다. 코드만으로 둘 이상의 정본 항목이 검색되면 교과명과 내용을 보여 주고 사용자가 구분해 선택하도록 한다. 서로 다른 성취기준을 코드가 같다는 이유로 합치지 않는다.

일괄 입력 결과는 ‘추가됨’, ‘이미 선택됨’, ‘찾지 못함’, ‘최대 7개 초과’를 구분한다. 정상 항목만 추가하고 기존 선택은 유지한다. 실패·초과 항목은 수정할 수 있도록 입력을 남긴다. 7개를 선택해도 제거 버튼과 결과 안내는 사용할 수 있어야 한다.

URL에는 선택한 고유 키와 모델을 기록한다. 새로고침·공유 시 같은 선택을 복원한다. URL에서 사라진 성취기준을 발견하면 안내하고, 이를 포함한 잘못된 AI 요청은 보내지 않는다. 목록을 불러오기 전 모델을 바꿔도 URL의 선택 키를 유실하지 않는다.

### 3.3 연결 분석

유효한 성취기준이 2개 이상이면 연결 분석을 시작한다. 연속 입력 중에는 짧게 기다렸다 마지막 선택 조합만 분석한다. 초기 설계값은 마지막 변경 후 700ms다.

분석 중에도 원문 확인, 성취기준 추가·제거, 모델 선택은 가능하다. 조합이 바뀌면 이전 조합의 분석 결과·애니메이션·미래 카드를 새 화면에 적용하지 않는다. 선택한 성취기준이 1개 이하가 되면 미래 열기 동작을 중단한다.

분석 결과를 받은 뒤 소속 관계와 교과 간 연결을 순서대로 보여 준다. 이 단계에서 호출할 수 있는 AI 작업은 연결 분석뿐이다.

### 3.4 연결 완료와 클릭 대기

연결 애니메이션이 끝나면 완성된 그래프와 연결 요약을 유지한다. ‘미래 보기’ 버튼을 표시하고 사용자가 검토할 시간을 준다. 시간이 지나거나 모델을 바꾸거나 창 크기를 조절해도 미래가 자동으로 열려서는 안 된다.

사용자가 ‘미래 보기’를 눌렀을 때만 미래 생성 요청과 시간의 고리 연출을 시작한다. 연타해도 같은 미래를 중복 생성하지 않는다.

### 3.5 미래 탐색과 프로젝트 시작

시간의 고리 연출 후 첫 미래를 표시한다. 생성이 아직 끝나지 않았다면 고리 연출을 무한 반복하지 않고 현재 관점의 대기 상태를 보여 준다. 이미 생성된 미래는 바로 읽을 수 있다.

이전·다음 버튼, 고리의 관점 선택, 좌우 방향키로 미래를 바꿀 수 있다. 휠·드래그 조작은 고리 영역에서만 사용하고, 카드 본문을 읽을 때 페이지 스크롤과 텍스트 선택을 방해하지 않는다.

‘이 미래로 프로젝트 시작’을 누르면 기존 프로젝트 생성 화면으로 이동한다. 성취기준, 제목 제안, 핵심 질문 또는 상황 설명을 전달한다. 최종 프로젝트 생성은 기존 생성 절차에서 완료한다. ‘성취기준 담기’는 중복 없이 기존 바구니에 추가하고 성공·실패 결과를 정확히 알려 준다.

## 4 그래프 데이터와 시각 규칙

### 4.1 관계 모델

큰 스톤 하나는 **선택한 성취기준 하나**를 뜻하며 교과명과 코드를 함께 표시한다. 같은 교과의 성취기준이 둘이면 큰 스톤도 둘이다. 교과는 성취기준의 속성이므로 별도의 교과 노드를 중복 생성할 필요는 없다.

작은 노드는 **해당 성취기준에 속한 키워드 하나**를 뜻한다. 모든 키워드는 자신의 성취기준 스톤과 직접 연결한다. 관계가 없는 키워드를 모양을 만들기 위해 삼각형·테두리·완전 연결 구조로 잇지 않는다.

| 요소 | 의미 | 식별과 표시 |
|---|---|---|
| 성취기준 스톤 | 선택한 성취기준 | 고유 키, 교과명, 코드, 구분 가능한 스톤 색 |
| 키워드 노드 | 원문에 있는 핵심 내용 | 성취기준 키와 키워드를 조합한 ID, 읽을 수 있는 이름 |
| 소속 연결선 | 이 키워드가 이 성취기준에 속함 | 큰 스톤에서 작은 노드까지 직접 연결 |
| 교과 간 연결선 | 서로 다른 성취기준의 키워드가 수업에서 이어짐 | 실제 키워드 노드를 끝점으로 사용 |
| 연결 이름과 이유 | 이어지는 교육적 근거 | 그래프의 연결 지점과 화면의 요약 목록에서 확인 |

같은 낱말이 서로 다른 성취기준에 있으면 소속이 다른 두 노드로 유지한다. 연결 끝점은 반드시 검증된 키워드 노드여야 한다. 세 개 이상의 키워드를 함께 연결할 때 중앙 합류 지점은 관계를 묶는 표시이며 새로운 성취기준·키워드로 해석되지 않게 한다.

선택되지 않은 성취기준, 존재하지 않는 키워드, 의미 없는 장식 연결선은 데이터 그래프에 넣지 않는다. 배경의 빛 먼지는 장식으로 분리한다.

### 4.2 스톤과 작은 별의 모습

큰 스톤은 면이 보이는 보석 형태로 표현한다. 과목별로 파랑·노랑·빨강·보라·주황·초록의 팔레트를 배정하고, 같은 과목의 스톤과 키워드는 같은 색으로 표시한다. 과목 수와 성취기준 수는 따로 집계하며, 실제 선택 수만큼 스톤을 표시한다.

키워드 노드는 작은 원형 보석을 기본으로 밝은 중심, 짧은 빛살, 절제된 광채를 더한다. 검은 점이나 배경의 미세한 별과 구분되어야 한다. 키워드 글자는 빛 효과와 별도로 선명하게 유지한다.

범례는 ‘큰 스톤: 성취기준 · 작은 별: 키워드 · 연결선: 소속과 교과 간 관계’로 표시한다. 색상 외에도 크기·라벨·선의 형태로 관계를 구분할 수 있어야 한다.

### 4.3 가독성과 배치

초기 설계값은 키워드 이름의 실제 화면 크기 데스크톱 16~20px, 모바일 최소 14px다. SVG 내부 좌표의 font-size만 확인하지 말고 축소 후의 실제 표시 크기를 검사한다. 긴 이름은 위치 조정 또는 줄바꿈으로 처리하며 원문을 임의 축약하지 않는다.

2개·4개·6개·7개 조합 모두에서 스톤, 키워드, 연결 이름이 화면 밖으로 잘리거나 주요 라벨과 겹치지 않아야 한다. 키워드의 소속 연결선은 항상 보이고, 교과 간 연결은 별도의 밝기·선·연출로 구분한다. 라벨을 이동하더라도 선의 끝점은 실제 노드 위치를 유지한다.

## 5 애니메이션 명세

### 5.1 연결 공개

먼저 큰 스톤을 배치하고 키워드를 표시한다. 각 스톤에서 자신의 키워드로 선이 그어지면서 소속을 보여 준다. 이후 검증된 교과 간 연결을 하나씩 강조한다.

각 연결에서는 관련 키워드가 동시에 밝아지고, 양쪽에서 빛과 키워드 이름의 잔상이 같은 합류 지점으로 이동한다. 그 지점에서 짧게 빛이 만나고 연결 이름이 나타난다. 원래 노드와 이름은 자리에 남아 그래프의 구조를 유지한다. 공개가 끝난 선은 남기고, 다음 연결을 보여 줄 때 기존 연결을 지우지 않는다.

초기 설계값은 연결당 약 1.2초, 마지막 연결 후 약 0.25~0.5초 정착이다. 첫 버전의 연결 수는 최대 7개로 제한한다. 모든 연결을 동시에 번쩍여 어느 키워드가 만났는지 알 수 없는 연출은 사용하지 않는다.

### 5.2 시간의 고리와 미래 공개

사용자가 클릭하면 스톤과 연결의 빛이 중앙으로 모이고, 초록빛 시간의 고리가 열린다. 고리와 문양의 회전·빛의 수렴으로 시간을 탐색하는 느낌을 만든다. 이후 8개 관점의 탐색 고리와 미래 카드가 등장한다.

초기 설계값은 빛 모으기 약 1.6초, 고리 전환까지 총 약 4초, 카드 등장 0.5~0.9초다. 실제 AI 응답 속도와 독립적으로 진행하며, 응답이 늦으면 생성 대기로 이어진다. 미래를 넘길 때에는 고리 회전과 카드 전환으로 선택한 관점을 알려 준다.

### 5.3 접근성과 성능

`prefers-reduced-motion`에서는 이동·회전·입자·섬광을 제거하거나 짧은 전환으로 축약한다. 연결 결과 확인과 명시적 클릭 순서는 동일하게 유지한다. 장식 Canvas와 카드 잔상은 보조기술과 키보드 탐색에서 제외한다.

버튼과 관점 선택에는 읽을 수 있는 이름과 포커스 표시를 제공한다. 입력창에 포커스가 있을 때 좌우 방향키로 미래가 바뀌지 않는다. 전체 화면을 덮는 반복 섬광을 사용하지 않는다.

화면 종료·조합 변경 시 RAF, 타이머, 이벤트 리스너, ResizeObserver를 해제한다. 종료된 화면의 요청 응답이 DOM이나 새 화면을 변경하지 않아야 한다.

## 6 AI 입력과 결과 품질

### 6.1 연결 분석

AI에는 서버에서 조회한 성취기준 정본과 해당 조합의 검증된 교육과정 연결만 전달한다. 클라이언트가 보낸 원문을 정본으로 신뢰하지 않는다.

초기 설계값은 성취기준별 핵심 키워드 3~5개, 연결 개념 0~7개다. 키워드는 원문의 내용 요소를 나타내는 명사구를 우선한다. 서버는 공백·문장부호 차이를 정규화해 원문 포함 여부를 확인하고, 원문에 없는 키워드는 제거한다. 충분한 키워드를 찾지 못했으면 수량을 채우기 위해 만들어 넣지 않는다.

연결에는 이름, 실제 키워드 끝점, 이유가 있어야 한다. 서로 다른 성취기준을 최소 두 개 포함해야 한다. 연결되지 않은 성취기준은 서버가 결과로부터 계산한다. 의미가 약한 조합과 연결 0개도 정상 결과로 인정하며 억지 연결을 만들지 않는다.

### 6.2 미래의 관점

첫 버전은 다음 8개 관점을 제공한다. 각 관점은 상황과 결과물 유형에 차이가 있어야 한다.

| 관점 | 수업의 방향 |
|---|---|
| 지역 문제 | 지역 현장 조사와 주민·기관을 위한 제안 또는 행동 |
| 학교 생활 | 학교 공간·규칙·일과의 개선과 시범 운영 |
| 데이터 탐구 | 데이터 수집·분석과 패턴 해석 |
| 과학 탐구 | 가설·변인·실험·관찰 |
| 창작 프로젝트 | 영상·전시·음악·이야기·디자인 제작 |
| 역사적 관점 | 과거 자료와 현재의 비교 |
| 진로·직업 | 직업인의 역할과 실제 업무 산출물 |
| 지구적 문제 | 국제 사례 비교와 세계 시민의 관점 |

### 6.3 미래 카드

미래 결과는 제목, 관점, 수업 상황, 핵심 질문, 성취기준별 역할, 활동 순서, 사용하는 자료, 학생 결과물, 평가 아이디어를 포함한다. 검증된 연결을 사용했으면 ‘연결 축’을 함께 보여 준다. 연결이 약하거나 특정 성취기준을 활용하기 어려우면 솔직한 메모로 설명한다.

서버는 JSON 구조와 필수 필드를 검증한다. 선택한 모든 성취기준의 역할을 한 번씩 포함해야 한다. 역할 누락·중복을 발견하면 제한된 보정 또는 재생성을 시도하고, 끝내 실패하면 해당 관점의 오류로 처리한다. 완성되지 않은 결과로 프로젝트 시작을 허용하지 않는다.

본문에 `S1`, `S2` 같은 내부 번호를 노출하지 않는다. AI가 반환한 텍스트는 화면 삽입 전에 안전하게 처리한다. 이 기능의 결과는 검증된 수업 효과의 예측이 아니라 AI가 제안한 수업 아이디어임을 알린다.

## 7 상태와 오류 처리

| 상태 | 화면과 허용 동작 | 다음 상태 |
|---|---|---|
| 입력 대기 | 0~1개 선택, 입력 방법과 예시 표시 | 2개 이상이면 연결 분석 |
| 연결 분석 | 선택 유지, 분석 중 안내, 미래 버튼 사용 불가 | 성공 시 연결 공개, 실패·지연 시 대체 안내 |
| 연결 공개 | 소속과 키워드 연결을 순서대로 보여 줌 | 공개 완료 후 클릭 대기 |
| 클릭 대기 | 완성된 그래프, 연결 요약, ‘미래 보기’ 버튼 | 사용자 클릭 시 미래 생성과 고리 연출 |
| 대체 안내 | 분석 실패와 연결 0개를 구분해 설명 | 재분석 또는 사용자가 미래 탐색 선택 |
| 미래 생성 | 고리 연출 후 현재 관점의 대기 상태 | 성공 시 미래 탐색, 실패 시 관점별 재시도 |
| 미래 탐색 | 결과 읽기, 관점 변경, 담기, 프로젝트 시작 | 조합 변경 시 새 연결 분석 |

연결 분석 지연의 초기 안내 기준은 25초다. 지연·실패 시 완료된 것처럼 가짜 연결을 표시하지 않는다. ‘연결 분석을 완료하지 못했습니다. 각 교과의 관점으로 미래를 볼 수 있습니다.’라는 안내와 ‘연결 다시 찾기’, ‘미래 보기’를 제공한다. 성공했지만 연결이 0개인 경우에는 ‘뚜렷한 키워드 연결은 찾지 못했습니다’라고 구분한다.

지연 결과가 뒤늦게 도착했을 때 클릭 대기 상태라면 최신 결과의 연결 공개로 돌아갈 수 있다. 이미 미래 탐색을 시작했거나 조합이 바뀌었으면 이전 결과를 적용하지 않는다.

| 장애 | 복구 요구사항 |
|---|---|
| 성취기준 목록 실패 | 빈 목록을 정상 결과로 취급하지 않고 ‘다시 불러오기’ 제공 |
| 로그인 만료 | 인증 갱신 또는 재로그인으로 안내. 가능한 선택 상태 보존 |
| 잘못된 코드·URL | 해당 항목을 알려 주고 정상 선택을 유지 |
| 연결 API 실패 | 실패 이유와 대체 흐름 제공. 미래 생성은 여전히 클릭 필요 |
| 미래 API 실패 | 해당 관점의 재시도 제공. 성공한 다른 관점과 선택 유지 |
| 요청 제한 | 서버의 재시도 가능 시점 안내. 자동으로 연속 재요청하지 않음 |
| 큐 대기·시간 초과 | 무한 대기를 종료하고 안내. 오래된 대기 요청 제거 |
| 캐시 저장 실패 | 이미 생성한 결과는 전달. 저장 실패를 생성 실패로 바꾸지 않음 |
| 담기·임시 저장 실패 | 성공으로 표시하지 않고 재시도 안내 |
| 페이지 이탈·빠른 변경 | 이전 화면 반영 금지, 대기 요청과 리소스 정리 |

## 8 서버와 데이터 계약

React·Vite 프론트엔드, Express API, 기존 Supabase 인증·정본 조회·캐시를 사용한다. 새 기능의 스타일·상태·캐시 이름을 기존 미래 보기와 구분한다. 현재 운영 인증을 유지하며 테스트를 위해 운영 인증이나 권한을 우회하지 않는다.

모든 API에 JWT 검증을 적용한다. `codes`라는 기존 필드명을 사용하더라도 값은 고유 성취기준 키를 우선한다. API가 표시 코드를 받는 경우 충돌 항목을 명시적으로 처리해야 한다.

| API | 요청 | 응답 |
|---|---|---|
| `GET /api/futures2/catalog` | 인증 정보 | `{ fields, rows }`: key, code, subject, subject_group, school_level, curriculum_category, content |
| `POST /api/futures2/bridges` | `{ codes: string[] }` | `{ bridges, cached }` |
| `POST /api/futures2` | `{ codes: string[], model: 'fast' \| 'precise', index: number }` | `{ future, cached }` |

`bridges`는 `keywords: { [standardKey]: string[] }`, `concepts: [{ label, ends: [{ key, word }], keys, why }]`, `isolated: string[]`를 포함한다. `future`는 6.3의 카드 필드와 관점 번호·모델·선택 키를 포함한다.

서버는 선택 수, 존재하는 키, 모델 값, 관점 번호의 정수 여부를 엄격히 검증한다. 첫 버전의 UI 관점 번호는 0~7이다. 기존 API가 0~29를 지원하는 것은 호환성 참고사항이며, 30개 미래 탐색 UI를 이번 범위에 추가할 근거가 아니다.

오류는 `{ error }` 형태의 사용자 안내를 포함한다. 잘못된 입력은 400, 인증 누락·만료는 401, 권한 부족은 403, 사용자·공급자 제한은 429, 서버·공급자 일시 장애는 5xx로 구분한다. 내부 프롬프트·키·토큰·스택 추적은 사용자 응답에 포함하지 않는다.

캐시 키에는 기능과 스키마 버전, 정렬된 성취기준 키, 모델, 관점 번호를 포함한다. 선택 순서가 달라도 의미가 같은 조합은 같은 캐시를 사용할 수 있지만, 스톤의 표시 순서는 사용자가 선택한 순서를 유지한다. 성취기준 내용·생성 규칙 변경 시 오래된 캐시를 구분할 버전 정책을 둔다.

## 9 10명 동시 사용과 요청 제어

10명이 ‘미래 보기’를 누르는 것은 AI 요청 10개와 같지 않다. 연결 분석, 현재 미래, 다른 관점의 미리 생성까지 합하면 더 많은 요청이 생긴다. 공급자의 동시 처리 수·분당 요청 수·분당 토큰 수를 함께 고려해야 한다.

새 구현의 초기 설계는 **현재 관점 먼저 생성, 이후 인접 관점 최대 2개 미리 생성**이다. 클릭 직후 8개 관점을 모두 생성하는 방식은 기본값으로 사용하지 않는다. 사용자가 관점을 바꾸면 그 관점을 우선 처리하고, 다른 미래는 필요할 때 생성한다.

| 제어 항목 | 필수 요구사항 |
|---|---|
| 미래 클릭 전 | 미래 생성 요청 0건. 연결 분석 요청만 허용 |
| 사용자별 요청 | 초기 설계값 분당 POST 40회. 조회와 채팅의 개별 제한과 구분 |
| 전체 AI 실행 | 서버 큐 사용. 동시 처리 수를 환경 설정으로 조정하고 공급자 한도 실측에 맞춤 |
| 요청 중복 | 같은 조합·모델·관점의 진행 중 작업은 하나로 합침 |
| 큐 우선순위 | 현재 관점 요청을 미리 생성 요청보다 우선 처리 |
| 대기열 | 실행 수뿐 아니라 최대 대기 수·대기 시간을 제한 |
| 전체 제한 시간 | 큐 대기·공급자 재시도·생성을 포함한 종료 시한 설정. 초기 설계값 미래 요청 180초 이내 |
| 취소 | 조합 변경·화면 종료 시 불필요한 대기 작업 취소. 다른 사용자가 기다리는 공유 작업은 유지 |
| 공급자 장애 | 제한된 재시도와 지연을 적용하고 반복 오류 시 미리 생성부터 중단 |
| 인스턴스 확장 | 메모리 큐·중복 제거·요청 제한이 인스턴스별로 분리되는지 확인하고 필요 시 공유 제어 사용 |

기존 채팅·자료 분석이 같은 AI 계정의 한도를 사용하는 점도 부하에 포함한다. 별도 큐가 있다는 이유만으로 계정 전체 한도가 분리되었다고 판단하지 않는다. 학교의 공용 IP를 쓰는 10명이 하나의 사용자 제한을 공유하지 않도록 로그인 사용자 ID를 기준으로 제어한다. 서비스 전체 보호용 IP 제한도 실제 연수 흐름에서 확인한다.

## 10 운영 관측과 장애 대응

요청 ID, 배포 버전, API 종류, 조합을 구분할 식별값, 캐시 여부, 큐 대기 시간, 생성 시간, 상태 코드, 공급자 오류 종류를 구조화해 기록한다. 인증 토큰·API 키는 기록하지 않는다. 사용자 프로젝트의 민감한 본문을 미래 기능 진단 로그에 포함하지 않는다.

운영자는 로그인 오류, 연결 실패, 미래 실패, 429 증가, 큐 적체, 잘못된 AI 응답을 구분해 확인할 수 있어야 한다. 화면에는 현재 단계와 재시도 방법을 표시하고, 개발자는 동일 요청 ID로 서버 기록을 찾아 원인을 진단할 수 있어야 한다.

| 상황 | 우선 대응 |
|---|---|
| 로그인·프로젝트 접근 장애 | 기존 서비스 전반 영향 확인, 최근 배포 확인, 필요 시 롤백 |
| 공급자 429·큐 적체 | 미리 생성 중단, 실제 한도 확인, 동시 처리 수 조정 |
| 연결 분석 장애 | 정직한 대체 안내로 탐색 지속, 오류 기록과 원문 검증 확인 |
| 일부 관점 생성 실패 | 성공 결과 유지, 실패 관점만 재시도 |
| 새 CSS·애니메이션의 기존 화면 영향 | 스타일 범위 확인, 영향 배포의 기능 변경만 되돌림 |

명세 작성만으로 자동 감시나 Codex의 즉시 대응이 실행되는 것은 아니다. 상시 감시가 필요하면 로그 접근 경로, 알림 조건, 대응 권한을 별도로 연결하고 실제 장애 신호로 확인해야 한다.

### 11.2 동시 사용 검증

운영과 같은 인증·네트워크·공급자 설정으로 다음 세 조건을 각각 확인한다.

1. 10명이 같은 조합을 사용한다. 캐시와 진행 중 요청 합치기가 실제로 작동하는지 확인한다.
2. 10명이 서로 다른 조합에서 첫 미래를 동시에 생성한다. 캐시가 없는 공급자 부하와 큐 대기를 측정한다.
3. 미래 생성 중 일부 사용자가 기존 채팅·자료 분석을 사용한다. 다른 기능의 오류와 공급자 한도 공유 영향을 확인한다.

계정 간 데이터 혼합, 중복 프로젝트, 응답 유실, 무한 대기는 없어야 한다. 정상 조건의 요청은 종료 시한 내 성공하거나 정확한 복구 안내를 제공해야 한다. 제한·장애를 주입한 검증에서는 해당 안내가 정상적으로 나타나야 한다.

실제 연수 준비 합격은 **의도적인 장애가 없는 10명 검증에서 현재 관점 10건 모두 생성 성공**을 조건으로 한다. 캐시 없는 빠른 모드의 초기 목표는 첫 미래 요청부터 결과 수신까지 P95 60초 이내다. 공급자 지연으로 목표를 넘기면 ‘합격’으로 기록하지 않고 동시 처리·미리 생성 정책을 조정한 뒤 다시 측정한다. 정밀 모드는 별도로 측정한다.

10명은 P95 추정에 작은 표본이므로 각 조건을 최소 3회 반복하고, 캐시 여부·개별 지연·최대 지연·오류·429·재시도·큐 대기·토큰 사용량을 함께 기록한다. 단일 AI 호출 성공이나 캐시 요청만으로 10명 동시 사용을 검증했다고 주장하지 않는다.

## 12 구현 순서와 배포 조건

1. 현재 운영 코드와 성취기준 정본을 기준으로 깨끗한 별도 작업 트리를 준비하고 롤백 기준을 기록한다.
2. 입력·고유 키·API 결과 구조를 확정하고 충돌 코드와 오류 입력을 검증한다.
3. 정적 그래프에서 모든 스톤→키워드→키워드 연결의 정확성과 가독성을 확인한다.
4. 연결 공개와 클릭 대기 상태를 구현하고 클릭 전 미래 요청이 없음을 검증한다.
5. 시간의 고리, 미래 카드, 오류 복구, 접근성을 구현한다.
6. AI 결과 검증, 캐시, 큐·중복 제거·시한·관측을 적용한다.
7. 실제 로그인 사용 흐름, 두 모델, 10명 동시 사용, 기존 주요 기능을 검증한다.
8. 미리보기 배포를 확인한 후 프론트엔드와 백엔드를 함께 반영하고 운영에서 핵심 흐름을 다시 확인한다.

배포 전에 실패 테스트, 인증·권한 회귀, 기존 화면의 스타일 충돌을 해소해야 한다. 명세의 신규 설계값은 실제 구현·테스트로 확인한 뒤 배포한다. 문서 작성 자체는 코드 수정·재배포·롤백을 실행하지 않는다.

롤백은 해당 기능의 변경을 식별할 수 있는 커밋 단위로 수행한다. 다른 사람의 미완료 작업과 이후 정상 변경을 보존하고, 원본 작업 폴더의 `reset --hard`나 강제 푸시를 사용하지 않는다. 프론트엔드와 백엔드의 직전 성공 배포를 기록하고, 임시 복사본에서 역적용 또는 복원 절차를 검증한다. DB 변경이 필요해지면 이전 코드와의 호환성과 데이터 복원 계획을 별도로 포함한다.

## 14 고등학교 연습 세트와 과목별 배치

2026년 10월 3일 사용자 추가 요구에 따라 두 연습 세트는 모두 고등학교 정본을 사용한다. 각 세트는 3과목·성취기준 6개이며, 선택 한도는 최대 7개다. 보통 3~4과목에서 성취기준 5~7개를 선택하는 이용 상황을 기준으로 배치한다.

| 세트 | 실제 성취기준 코드 |
|---|---|
| 음악 · 수학 · 국어 | 음악 `[12음02-01]`, `[12음03-03]`; 공통수학1 `[10공수1-03-01]`, `[10공수1-03-03]`; 공통국어1 `[10공국1-06-01]`, `[10공국1-06-02]` |
| 미술 · 정보 · 영어 | 미술 `[12미01-03]`, `[12미02-02]`; 정보 `[12정02-03]`, `[12정02-04]`; 공통영어1 `[10공영1-02-01]`, `[10공영1-02-07]` |

같은 과목의 성취기준을 같은 영역 안에 모으고 색을 일치시킨다. 각 성취기준은 독립 스톤과 고유 키를 유지하며 자신의 원문 키워드에 직접 연결된다. 성취기준 7개를 7과목으로 해석하거나, 모든 스톤을 고정된 작은 타원 안에 배치하지 않는다. 데스크톱은 과목별 열을 사용하고, 모바일은 과목 영역을 세로로 재배치해 글자를 작게 줄이지 않는다.

정본의 공통과목 1·2가 하나의 과목명으로 저장되어 있어도 코드에서 실제 과목을 구분해 표시한다. 쉼표가 포함된 고유 키는 JSON 배열 형식의 URL 값으로 보존하며 기존 쉼표 구분 URL도 계속 지원한다.

두 기본 세트는 언제든 선택 조합을 교체할 수 있도록 입력 패널에 제공한다. 클릭하면 실제 정본의 키를 조회해 선택하며, 연결 분석만 시작한다. 미래 생성은 연결을 확인한 뒤 사용자가 ‘미래 보기’를 눌렀을 때 시작한다.

추가 검수는 두 고등학교 세트의 실제 AI 생성, 음악 세트에 `[12음03-01]`을 추가한 3과목·7개 조합, 미술 세트에 `[10공수1-03-03]`을 추가한 4과목·7개 조합을 포함한다. 실제 응답의 역할 수, 원문 키워드, 연결 끝점, 화면 라벨 겹침과 모바일 너비를 확인한다. 단일 조합 검증은 10명 동시 사용 검증과 구분해 기록한다.
